# Empathy Pass Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Make the boss fight forgiving enough that about 80% of walk-up players win. The pieces are:
- logarithmic beam AMP
- forgiving hits
- a flash plus slow-mo when E is ready
- rare power-ups
- a low-HP warning
- a round log and a read-only dev console to measure the real win rate

**Architecture:** Every gameplay change lives in the fixed-step simulation (`src/game/`) and is unit-tested without a browser. Slow-mo is a time scale applied inside `stepWorld`. Power-ups are split across two modules:
- `powerups.ts`: spawning and motion
- `pickups.ts`: collecting and effects

The split keeps the imports acyclic. The round log (`src/tally.ts`) is plain data in `localStorage`. The dev console replaces the one-line F3 overlay.

**Tech Stack:** TypeScript (strict), Vite, Vitest (+ happy-dom for DOM tests), raw WebGL2. No new dependencies.

**Spec:** `docs/superpowers/specs/2026-11-19-empathy-design.md` (main game spec: `docs/spec.md`)

## Global Constraints

- Work on branch `feat/empathy`. **Commit only if the owner has said to.** Each task ends with a green full suite (`npm test`). The commit steps below run only once the owner has agreed to commits.
- Commit subjects are imperative and ≤72 characters. The body explains why and ends with `Co-Authored-By: Claude Opus 5.5 <noreply@anthropic.com>`.
- Every tunable is a single value in `src/config.ts`. No magic numbers in game code.
- No allocation inside `stepWorld`. Entities come from `Pool`s. Scratch objects are module-level and reused, like `candidates` and `beamBox` in `combat.ts`.
- Boxes are centre-based (`x, y` = centre). `overlaps` treats touching as not overlapping. `Renderer.rect` alone takes a top-left corner.
- Tests sit next to the code as `*.test.ts`. Use the helpers in `src/game/testUtils.ts` (`makeWorld(mutate?)`, `fakeInput`, `run`, `shoot`, `enemyShot`, `drone`). DOM tests start with `// @vitest-environment happy-dom`.
- On Git Bash, run tests from a `C:/...` path or use PowerShell (README).

  - `rapid` and `clear` always
- Walk `POWER_UP_KINDS` in order, summing the weights of the eligible kinds. Return the first kind where `roll × total < cumulative`. Fall back to the last eligible kind.
- No arrays are created.

**`maybeDropPowerUp`:**
- If `w.rng() < dropChance` and the pool has room, place a power-up at `x`, with `y` clamped to `[area.y, area.y + area.h]`.
- The kind comes from `choosePowerUpKind(w, w.rng())`.

**`updatePowerUps`:**
- If a power-up is within `magnetRadius` of the player's centre, it moves straight at the player at `magnetSpeed`.
- Otherwise it drifts left at `driftSpeed` with `y = baseY + sin(age·bobFreq·2π)·bobAmp`.
- When it leaves magnet range, set `baseY` to the current y.
- Release it when `x < -size`.
- It keeps moving after the round ends.

**`killDrone`** gains a `canDrop` flag:
- `true` for kills by bullets and the beam
- `false` for kills by `clearScreen`

**`resolvePickups`:**
- Only while playing.
- Overlap with the full `w.player` box applies the effect, pushes `powerUpCollected`, sets `lastPickup` and releases the power-up.

**`applyPowerUp`** effects, per the design §5.7:
- `rapid` sets `p.rapid = rapidTime`.
- `health` adds a heart, capped at `cfg.player.hp`.
- `charge` calls `readySpecial`.
- `clear` calls `clearScreen`.

**`updatePlayer`** decrements `rapid` (clamped at 0). The fire interval is `1 / (fireRate × (rapid > 0 ? rapidMultiplier : 1))`.
